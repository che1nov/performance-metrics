# Метрики производительности — домашнее задание 1

**Дисциплина:** Управление производительностью приложений. **Тема:** понимание и измерение метрик производительности.

**[Отчёт с результатами и скриншотами Grafana](report/report.md)** · [Исходные измерения](results/) · [Сценарий JMeter](load/compare.jmx)

Проект сравнивает обработку одинакового блокирующего ожидания на обычных и виртуальных потоках. Spring Boot MVC + Actuator/Micrometer экспортируют метрики в Prometheus. Grafana автоматически получает источник данных и дашборд Rate, Errors, Duration.

## Запуск

Требуются **JDK 21+**, Maven 3.6.3+, Docker с Compose. Для нагрузочного теста — JMeter 5.6.3 и Python 3. Виртуальные потоки в этом проекте используют стабильный API Java 21; JDK 8 из общего списка задания для этой части недостаточно. На проверочном компьютере приложение запущено на JDK 25, JMeter — на JDK 17.

Из папки проекта:

```sh
mvn clean verify
docker compose up -d
java -Xms256m -Xmx512m -jar target/performance-metrics-1.0.0.jar
```

При нескольких JDK задайте `JAVA_HOME` на JDK 21+ перед Maven и используйте соответствующий `java` для JAR. Приложение остаётся запущенным в терминале.

- Приложение: http://localhost:8082/actuator/health
- Метрика: http://localhost:8082/actuator/metrics/http.server.requests
- Экспорт Prometheus: http://localhost:8082/actuator/prometheus
- Prometheus: http://localhost:9091/targets
- Grafana: http://localhost:3001/d/performance-red

Grafana настроена на локальный просмотр без входа. Порты контейнеров доступны только на 127.0.0.1. Приложение слушает 8082 на интерфейсах хоста, чтобы к нему мог обратиться контейнер Prometheus через `host.docker.internal`. Это учебная конфигурация для локального стенда.

## Эндпоинты работы

```sh
curl 'http://localhost:8082/work/platform?delayMs=500'
curl 'http://localhost:8082/work/virtual?delayMs=500'
curl -i 'http://localhost:8082/work/virtual?delayMs=500&fail=true'
```

Первые два возвращают HTTP 200 и поля `mode`, `virtualThread`, `thread`, `workMillis`, `simulatedFailure`. Третий преднамеренно возвращает HTTP 503 для проверки Errors. `delayMs`: от 1 до 5000; неверное значение даёт HTTP 400.

`workMillis` измеряет выполнение внутри worker. Длительность `http.server.requests` и время JMeter дополнительно включают ожидание очереди и обработку HTTP. Поэтому для анализа клиентской задержки используются именно последние две метрики.

Контроллер возвращает `CompletableFuture`, освобождая поток Tomcat на время работы. Оба метода вызывают один `WorkService`; меняется только исполнитель:

- обычные потоки: 16 workers, очередь `ArrayBlockingQueue` на 1024 задачи;
- виртуальные потоки: отдельный виртуальный поток на каждую задачу.

Задержка `Thread.sleep(500)` моделирует блокирующее ожидание, а не вычисления или реальный внешний API. Размер обычного пула задаётся `--lab.platform-threads=16`. Разница размеров пула — существенная часть эксперимента, а не доказательство универсального ускорения виртуальными потоками.

## Ручное измерение COUNT

Сначала выполните один запрос: метрика создаётся после появления обработанного запроса.

```sh
curl 'http://localhost:8082/work/platform?delayMs=3000'
curl 'http://localhost:8082/actuator/metrics/http.server.requests?tag=uri:/work/platform'
```

В массиве `measurements` найдите запись со `statistic: "COUNT"`. Во время нагрузки снимите `COUNT₁`, через 10 секунд — `COUNT₂` с тем же тегом. Формула:

```text
throughput = (COUNT₂ − COUNT₁) / фактическое_число_секунд
```

COUNT учитывает завершённые запросы, включая ответы с ошибкой. Незавершённый долгий запрос ещё не увеличивает COUNT. Фильтр `uri` обязателен, чтобы запросы `/actuator/*` не попадали в числитель. Между отсчётами нельзя перезапускать приложение: счётчики сбросятся.

## Воспроизведение замеров JMeter

Скачайте JMeter с [официального сайта](https://jmeter.apache.org/download_jmeter.cgi). Для проведённых измерений использован 5.6.3; архив проверен по официальному SHA-512. Распакуйте его, например, в `.tools/apache-jmeter-5.6.3`.

Сохранённые в Git результаты относятся к уже выполненному опыту. Для нового опыта переместите папку `results` в резервную копию: скрипт намеренно не дописывает новые запросы в существующие JTL.

```sh
mv results results-original
python3 scripts/measure.py --jmeter /absolute/path/apache-jmeter-5.6.3/bin/ApacheJMeter.jar
```

Если JMeter следует запускать на другой Java, задайте `JMETER_JAVA_HOME` на её каталог. Скрипт запускает JMeter в режиме CLI через JAR, поэтому поддерживает пути с пробелами.

Последовательность: один запрос длительностью 3 секунды и контроль COUNT за 10 секунд; 60 секунд нагрузки на platform; пауза 6 секунд; 60 секунд на virtual; пауза 6 секунд; 35 секунд virtual с управляемыми ошибками. В обеих основных фазах 200 клиентов, разгон 5 секунд, задержка 500 мс. После 15 секунд прогрева берутся четыре отсчёта COUNT, образующие три соседних окна по 10 секунд. Реальное Δt измеряется монотонными часами с учётом времени HTTP-опроса.

В фазе ошибок каждый десятый клиент всегда отправляет `fail=true`: около 10% ответов должны быть HTTP 503. Фактическая доля вычисляется из JTL. В основных двух фазах ошибки не допускаются.

Скрипт сохраняет сырые Actuator-ответы и метки времени в JSON, запросы JMeter в CSV `.jtl`, агрегаты в `summary.json`. Пропускная способность JMeter за весь запуск включает разгон и завершение очереди, поэтому отличается от стационарных 10-секундных окон Actuator.

## Prometheus и Grafana

Конфигурации находятся в `monitoring/`. Prometheus собирает метрики каждые 2 секунды. Grafana использует `rate(...[20s])`, поэтому изменения нагрузки сглаживаются на 20-секундном окне. Панели исключают запросы мониторинга и фильтруют только `/work/platform` и `/work/virtual`.

- **Rate:** сумма скорости роста `http_server_requests_seconds_count` по URI, запросов/с.
- **Errors:** скорость ответов HTTP 5xx по URI. В основной нагрузке — ноль, в фазе управляемых отказов — положительная.
- **Duration:** `rate(sum) / rate(count)` для средней задержки и `histogram_quantile(0.95, ...)` для p95. p95 Prometheus — оценка по бакетам, p95 JMeter — квантиль отдельных наблюдений.

Наблюдения Prometheus хранятся в Docker volume 7 дней. Скриншоты и выгрузка временных рядов в отчёте сохраняют результат исходного опыта; новый запуск сам по себе не создаст исторические точки из отчёта.

Остановка: Ctrl+C в терминале приложения, затем `docker compose stop`. Эта команда сохраняет данные мониторинга.

## Проверки

`mvn verify`: 4 HTTP-теста с настоящим сервером. Проверяются тип worker-потока, обработка неверной задержки, HTTP 503 и наличие экспортируемых метрик Prometheus. Контроль COUNT и нагрузочные измерения выполняет `scripts/measure.py`.

Отчёт можно открыть прямо в GitHub. Ссылку на `report/report.md` нужно самостоятельно прикрепить в личном кабинете курса.
